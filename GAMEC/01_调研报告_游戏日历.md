## 0. 一句话结论

**没有现成项目能直接满足需求，但也不需要从零造轮子。**
市面上的游戏追踪工具（Backloggd / GG App / Playnite）都是**列表视角**——按状态、评分、平台分类；而你要的是**时间视角**——"未来我要买什么"和"过去我玩了什么"放在同一个日历上。这个视角是明确的产品空白。

技术上，日历渲染有大量成熟 MIT 库可用；真正的工作量在**数据层**（通过登录拉取 Steam 数据 + 本地持久化）和**领域建模**（"想买/已买/在玩"的状态 + 时间事件）。

**v0.5 三条结论**：

1. **时间戳以成就解锁时间为主，是可行的。** `GetPlayerAchievements` 的 `unlocktime` 是唯一能**回溯到过去**的精确时间证据；密集的解锁时间簇 = 一次游玩。局限是只覆盖"有成就且确实解锁"的时段。
2. **首次游玩时间可以拿到。** `ClientGetLastPlayedTimes` 返回 `first_playtime`，属于 steamclient 客户端协议方法，**需账号登录调用**——与登录路线天然契合，MVP 就该用上。
3. ~~**购买时间登录后全自动。**~~ **入库时间已放弃**：`CMsgClientLicenseList`（TCP 协议）暂不考虑。购买时间 v1.1 改走**商店购买历史页**（web session cookie，日粒度，见 [[03_Steam信息获取文档|03]] §4.1），购买事件回到时间轴。

> **不再做**：会话级采集（`localconfig.vdf` / 进程监听）已决定暂不实现（成本高、复杂度高），时间戳精度退到"天/成就级"。

## 1. 同类产品扫描（竞品与缺口）

| 产品 | 形态 | 核心视角 | 与本项目的关系 |
|---|---|---|---|
| **Steam 原生愿望单** | Steam 客户端/网页 | 列表 + 降价/发售邮件提醒 | 提供数据源，但只有"未来"没有"过去"，无日历视图 |
| **Backloggd** | Web，闭源 | 库存 + 日志 + 评分社区 | 最接近的"游玩回顾"，但强社交、无发售日历、数据不在本地 |
| **GG App / SavePoint** | 移动端，闭源 | 收藏 + 进度 | 移动体验好，但闭源、无法自定义、无 Steam 深度打通 |
| **Playnite** ★13.3k, MIT, C# | Windows 桌面，开源 | 统一启动器 + 库管理 | **最值得研究的工程参考**：已解决 Steam/Epic/GOG 库导入、游玩时长记录、插件 SDK。但它是启动器，不是日历 |
| **GameVault / Gameyfin** ★1.0k, AGPL-3.0 | 自部署 Web | "游戏界的 Jellyfin"（管理本地游戏文件） | 场景不同（管本地安装包），但元数据抓取与刮削逻辑可参考 |
| **GG.deals / IsThereAnyDeal** | Web，闭源（有开放 API） | 价格追踪 + 发售日历 | 提供数据源（历史低价、愿望单降价）；价格能力本项目**暂不接入** |
| **HowLongToBeat** | Web，闭源（无官方 API） | 通关时长众包数据 | 提供"这游戏要玩多久"的补充字段（可选） |

### 缺口定位

1. **没有产品把"未来购买计划"和"过去游玩历史"放在同一个日历上。** 前者被愿望单工具占据，后者被日志类工具占据，两边不通。
2. **没有产品做"消费节奏 × 发售节奏"的日历。** 你的隐含需求是决策辅助：这个月有三款想买的游戏同时发售，我该买哪个 / 分几个月买。
3. **开源自托管方案里，没有一个是"个人游戏编年史"定位的。** 现有开源项目都在解决"管理文件"或"统一启动"，不解决"回顾我的游戏人生"。

## 2. 日历 / 时间线开源库对比

⚠️ **重要前提**：本项目需要的**不是**"会议日程日历"（FullCalendar 那类为了处理"周三 14:00-15:30 重叠会议"而设计的库）。你的事件是**全天级、低密度**的（某天发售、某天购买、某天解锁成就）。用日程库会引入大量用不上的复杂度。

### 2.1 月历 / 日程型

| 库 | Star | 协议 | 技术栈 | 评价 |
|---|---|---|---|---|
| **FullCalendar** | 20.5k | MIT（核心）；Premium 插件另行商业授权 | TS，React/Vue/Angular 封装 | 生态最大、文档最全。但为日程场景设计，API 面积大；时间轴/资源视图属付费 Premium |
| **react-big-calendar** | 8.7k | MIT | JS/React | gcal 风格，轻量，可换日期库（date-fns / dayjs）。适合快速搭月视图 |
| **Schedule-X** | 2.4k | MIT | TS，React/Vue/Angular/Svelte/Preact | 定位就是"FullCalendar 的现代替代"，API 更干净，多框架适配好。**新项目首选之一** |
| **Event Calendar (vkurko)** | 2.2k | MIT | Svelte 5 / 独立 bundle，35kb (br) | 极轻量、零依赖、含资源时间轴视图。若不想引入重框架，是很好的选择 |

| 库 | Star | 协议 | 说明 |
|---|---|---|---|

| **react-calendar-timeline** | 2.1k | MIT | TS 重写版，甘特/泳道式时间线。同上，暂不需要 |

> ~~cal-heatmap（年度热力图）~~ —— **已按需求排除**，不做热力图。

### 2.3 视图形态（v0.5 更新）

~~双视图：横向时间轴 + 常规月历~~ —— **已撤销**。v0.5 起界面为**单一日历视图**：

- 日历格子显示**时点事件**（发售 / 购买 / 首次游玩 / 成就簇），图标 + 色点。
- 顶部按钮 / 左右滑动切换时间，时间戳可滚动。
- 促销日等多事件用 "+N" 折叠。
- **已发售的愿望单游戏不进日历主体**，归入独立清单。

### 2.4 选型建议

- **月历** → 优先 **Schedule-X**（MIT，多框架，API 最干净）或 **Event Calendar**（MIT，35kb，零依赖）；想自己掌控就**手写 7×6 CSS Grid + dayjs**。
- **时间线库不再需要**（单一日历视图）。
- **省下的复杂度用在数据层。** 这个项目的难点从来不在渲染。

> ~~§2.5 月视图信息架构（五层 L0~L3、密度自适应等）~~ —— **已撤销**。界面极简后不再需要"格子放不下卡片"的解决方案，格子只放图标 + 色点。

### 3.1 合规红线（必须写进技术方案）

1. **SteamDB 不抓。** 其 FAQ 原文："there's a chance you'll get automatically banned for doing so"。历史价格改用 IsThereAnyDeal 官方 API（若未来接入）。
2. **登录凭据（账号/密码/令牌/2FA）不外泄、不上传。** 登录态只保存在用户本地（加密存储），绝不进任何远程服务或打包进二进制。
3. **Steam API Key 不外泄**（若仍用 API 兜底元数据）：Key 存本地配置，不硬编码。
4. **抓取 Store API 必须缓存。** 元数据缓存 30 天；价格缓存 6~24 小时；只在用户主动刷新时打接口。
5. **分享页面只输出用户自己的数据 + 官方素材链接**（若未来做 X-3 导出）。

### 3.2 数据源分工建议（v0.5：登录为主）

```
登录（SteamKit / node-steam-user）统一入口：
  "未来要买什么"  ← GetWishlist（愿望单）+ Store API 发售日/元数据
                    已发售的愿望单游戏 → 独立清单，不进日历主体
  "过去玩了什么"  ← GetPlayerAchievements.unlocktime（成就时间戳，主）
                   + ClientGetLastPlayedTimes.first_playtime（首次游玩，起点）

API Key 兜底（可选）：GetOwnedGames 元数据 / Store API 补中文名与封面
```

> **v0.5 范围决策**：会话级采集（`localconfig.vdf` / 进程监听）**暂不实现**；价格/市场数据**暂不维护**；非 Steam 游戏**暂不做**（V0.1 只做 Steam）。

### 3.3 【核心结论】时间戳怎么来？—— 以成就解锁时间为准

**Steam 自己不记录单次会话。** 它只存累计总时长、最近两周时长、最后一次游玩时间戳；客户端本地也不留会话日志。桌面端虽可通过轮询 `localconfig.vdf` 推算会话起止，但**已决定暂不实现**（成本高、有挂机/离线等误差）。

因此，**历史游玩的时间证据主要靠成就解锁时间**：

- `ISteamUserStats/GetPlayerAchievements` 的 `unlocktime` 是唯一能**回溯到过去**的精确时间戳。
- 密集的解锁时间簇 = 一次游玩会话；稀疏的单点 = "这天玩过"。
- 局限：只覆盖有成就、且你确实在解锁的时段；刷完成就之后的游玩看不到。

**配合两条时点证据，日历的"过去"就有骨架了：**

| 证据 | 来源 | 覆盖 |
|---|---|---|
| 成就解锁时间 `unlocktime` | `GetPlayerAchievements` | 有成就且解锁过的时段（**主**） |
| 首次游玩时间 `first_playtime` | `ClientGetLastPlayedTimes`（登录） | 每款游戏的起点 |

> ⚠️ **仍然存在的历史缺口**：两条证据都无法覆盖"没有成就/没解锁成就"的游玩；真正精确到分钟的历史依然没有。但对"哪年/哪月沉迷过什么"这个产品诉求，成就时间戳 + 首次游玩已经足够支撑日历。

### 3.4 ~~【更新】游戏购买时间能采集到吗？~~（已放弃）

> ⏸ **已放弃（v1.0 后）**：许可证入库时间（TCP 协议 `CMsgClientLicenseList`）暂不考虑，本节研究结论仅作历史存档，不再进入方案。

**能，登录即可全自动。**

| 路径 | 能拿到什么 | 认证要求 | 评价 |
|---|---|---|---|
| **Steam Web API（API Key）** | ❌ 什么都拿不到 | — | 此路不通 |
| **客户端协议 `CMsgClientLicenseList`** | ✅ 每个 package 的 `time_created`（入库时间）、`payment_method`、`purchase_country_code` | **账号登录**（用户名密码 / QR / 2FA） | **v0.5 选定路径** |
| 网页 `/account/history/` | ✅ 日期、描述、付款方式、金额 | 浏览器 Cookie | 备用（需处理分页与登录态） |
| CSV 导入 | 用户手动 | — | **已弃用**（改登录全自动） |

### 关键取舍

`CMsgClientLicenseList` 路线用 SteamKit / node-steam-user **以真实账号登录**，会引入密码/令牌管理、2FA 流程、登录会话维护。对**纯自用的本地应用**可接受，且换来购买时间全自动。

三个坑（沿用）：

1. **`time_created` 是"许可证创建时间"，不完全等于"购买时间"**。Key 激活、赠送、捆绑包、免费领取都会产生 license。对"何时拥有"准确，对"花钱那一刻"未必。
2. **`package_id` ≠ `appid`**，需再查 PICS（`PICSGetProductInfo`）拿到 package 含哪些 app。
3. **退款重买、家庭共享**会让数据复杂。

### 3.5 【更新】首次游玩时间与历史回填

**首次游玩时间（`first_playtime`）已确认可获取**，这是本次最重要的确认：

- `IPlayerService/ClientGetLastPlayedTimes` 属于 **steamclient 客户端协议方法**（`steammessages_player.steamclient`），**通过登录调用**，返回每款游戏的 `first_playtime`（首次游玩时间戳）、`last_playtime`、分平台（Windows/Mac/Linux/Deck）首次/最后游玩。
- 意味着即使今天才装应用，日历也能立刻标出"我是 2017 年 8 月第一次打开《巫师3》的"。
- 待验证（低风险）：登录后实际调通一次，确认返回结构与字段有值。

**历史回填（`GetUserYearInReview`）暂缓。** Steam Replay 自 2022 年起有月度级历史，可用于回填（P-10）；但年度总结（P-6）已砍，回填优先级降为 P1，待日历跑通后再评估。

## 5. 技术选型初步建议

基于"本地桌面优先 + 登录拉数据 + 极简单一日历"这一约束：

| 层 | 建议 | 理由 |
|---|---|---|
| **应用框架** | **Tauri 2**（或你更熟的栈，**待你最终拍板**） | 桌面 + 后期 iOS/Android 同套代码，包体小；Rust 后端可安全保管登录态 |
| 备选 | Electron | 生态更成熟；若走 Node 生态，`node-steam-user` 登录更顺 |
| **Steam 登录** | **SteamKit（C#/Rust 绑定）或 node-steam-user（Node）** | 视应用框架定：C#→SteamKit；Node→node-steam-user |
| **前端** | React/Vue + TypeScript + dayjs | 日历库生态都在这边 |
| **日历渲染** | Schedule-X / Event Calendar / 手写 CSS Grid | 见 §2.4 |
| **本地存储** | **SQLite** | 成就/首次游玩会产生大量时序行，需要真正的查询能力 |
| **登录态保存** | 本地加密存储（如 OS keychain / DPAPI） | 凭据绝不上传、不打包进二进制 |

### 待决策/待核实项

- [ ] 账号登录（SteamKit / node-steam-user）能否稳定跑通（含 2FA、登录态维护）——**最高优先级，先于一切界面工作验证**
- [ ] `ClientGetLastPlayedTimes` 的 `first_playtime` 登录后是否真有值——**第二优先级，十分钟能验完**
- [ ] 成就 `unlocktime` 的覆盖密度是否足以支撑日历（拿自己 3 款老游戏看时间戳分布）
- [ ] 愿望单中"已发售"状态的稳定识别方式（`GetWishlist` + Store API 发售日对比）
- [ ] Store API 实际限流阈值与中文名覆盖率（中英文名都可接受）
- [ ] 技术栈是否确定 Tauri 2（暂继续考虑）

> ~~已撤销项~~：`localconfig.vdf` 字段/写入时机验证、`GetUserYearInReview` 返回结构验证、双进程架构、进程监听性能、SteamKit 协议分发方式（已并入登录路线评估）。

## 6. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| **历史游玩数据不可得（无成就/未解锁成就的游玩）** | 日历"过去"部分有空缺 | 成就时间戳 + 首次游玩两证据撑骨架；明确产品叙事"从有记录处开始" |
| **登录态失效 / 2FA 频繁要求** | 数据拉取中断 | 本地缓存已有数据，产品降级可用；登录态本地加密 + 续期 |
| **成就 `unlocktime` 覆盖密度不足** | 日历稀疏 | 首次游玩补齐时点；必要时再评估手动补录（P-4） |
| **Steam 内部接口（愿望单/客户端协议）失效或变更** | 数据源中断 | 抽象为 Provider 接口；降级到 Store API / 手动刷新 |
| **Store API 限流/封禁** | 元数据刷新失败 | 强缓存 + 指数退避 + 失败不阻塞 UI |
| **凭据安全（登录令牌/密码保管）** | 用户信任受损 | 本地加密存储、绝不上传、明示用途 |
| **一个人做，范围失控** | 项目烂尾 | 严格 v0.1 极简范围，砍掉项见 [[04_未来规划_游戏日历|未来规划]] |
