## 0. 本轮目标与边界

**目标**：收敛 [[05_后端接口文档|05]] §8 的缺口，交付一套**登录可用 · 采集完整 · 一次性全量下发**的 REST 服务，能用真 Key 跑通并自证。

**本轮不做**（非「永久不做」，属 V0.1 内的后续阶段，暂不移入 [[04_未来规划_游戏日历|04]]）：

- 成就展示三件套（05 §8 缺口 C）——待 [[07_视图范式_游戏日历|07]] §4.8 悬浮 panel 定稿后单独排；
- 色值 API ①（SteamGridDB 等第三方主色接口）——主题色只走②本地取色 / ③回退；
- 登录态之外的安全细化（限流分级）、Postgres 上云与运维；
- 前端一切内容。

## 2. P0 · Steam 登录链路

现状：`POST /auth/steam` 收客户端的 `steam_access_token`，调 `ISteamUserOAuth/GetTokenDetails/v1/` 换 SteamID64。**这条链路从未被真实调用过一次**——测试里的 `FakeSteam` 永远返回成功。

### 2.1 先解一个文档冲突

| 出处 | 写法 |
|---|---|
| [[05_后端接口文档\|05]] §2 | SteamKit 登录（**客户端**）→ 后端校验并取 SteamID |
| [[01_客户端开发文档\|01]] §3 表格 | Steam 登录 = **后端承担**（SteamKit / node-steam-user） |

两处对「谁执行登录」不一致。按 README 规则 2「冲突时先改文档再改代码」，**P0-2 先定死再动代码**。

**✅ 已定死（2026-08-28，随 OpenID 决策一并解决）**：不是「后端校验」vs「后端跑 SteamKit」二选一，而是拆成两层——

- **Layer 1（默认）**：纯后端 **Steam OpenID 2.0** 重定向 + 回调验签，前端零 SteamKit / node-steam-user 依赖，只是一次浏览器跳转。05 §2「SteamKit 登录（客户端）」与 01 §3「Steam 登录 = 后端承担（SteamKit / node-steam-user）」两处写法都已作废，统一改成 Layer 1 OpenID（见下 §2.3 方案 B）。
- **Layer 2（opt-in）**：现有 05 §2.1 的 steam-session 侧车（`node-steam-user`，后端承担，含 QR / 账密 + 2FA）保持不变，仅在用户要看愿望单 / 购买历史 / 私密截图时触发。

回写状态：05 §2 已回写；01 §3 待回写（见 T18）。分层依据与数据源公开/私密分类见 [[03_Steam信息获取文档|03]] §2a。

### 2.3 P0-3 的三条备选

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A · 本地验 JWT**（若 P0-1 显示新版 access_token 是 JWT） | 后端用 Valve 公钥验签，直接解出 `sub` = SteamID64 | 未采用——`ISteamUserOAuth` 是否还发新版 JWT 未经验证，且仍需客户端先跑 SteamKit 拿 access_token，不满足「零客户端依赖」 |
| **✅ B · Steam OpenID 2.0（已选定，2026-08-28）** | 后端做 `steamcommunity.com/openid/login` 的 realm + return_to + 签名校验 | Valve 唯一长期公开稳定的登录方式，不碰用户密码，零客户端依赖。原「代价」已消：05 §2「客户端用登录态拉 GetWishlist」这条路线已改道——愿望单换成官方 `IWishlistService/GetWishlist`（免 Key，公开愿望单直接查，私密才降级 Layer 2 session cookie），见 [[03_Steam信息获取文档|03]] §2a |

## 6. P4 · 下发接口

### 6.1 接口形状决策

**`/timeline` 用「游戏字典 + 扁平事件」，不内嵌 `GameBrief`。**
现在 `/calendar` 每个事件都内嵌完整 `GameBrief`（名称 + 封面 URL + 主题色）。全量下发时一款游戏有几百个成就簇事件，每个都重复带一遍封面 URL——几 MB 的纯冗余。

```jsonc
{
  "generated_at": "2026-08-28T04:00:00Z",
  "range": { "from": "2013-05-02", "to": "2026-08-28" },
  "games":  [ { "appid": 1245620, "zh": "…", "en": "…", "cover": "…", "portrait": "…", "theme_color": "#B0761A" } ],
  "events": [ { "d": "2026-08-03", "t": "achievement", "n": 12, "m": 603, "a": 1245620 } ],
  "screenshots": [ { "id": "…", "a": 1245620, "ts": 1787000000, "thumb": "…", "url": "…", "p": 0 } ]
}
```

粗估 events ~5k、screenshots ~2k、games ~500 → 裸 600 KB，gzip 后约 150 KB。

> [[07_视图范式_游戏日历|07]] §2「不得引入第三个数据接口」约束的是前端 `getDayGroups` / `getDayDetail` 两个函数，不约束后端路由数——`/timeline` 仍只喂这两个函数。

## 10. 验收标准

1. 真账号登录成功，SteamID64 与本人一致；六条失败路径全部有断言。
2. 绑 Key 后一轮完整同步跑通，`games` / `play_days` / `achievements` / `screenshots` 四张表都有数据。
3. `games.theme_color` 命中率达标（阈值由 S-B 结果定），聚合不再恒用回退色 `#6D4AE0`。
4. `/timeline` 一次返回、gzip 后 < 500 KB、二次请求 304；`/calendar/day` 的 `screenshots[]` 非空。
5. `pytest` 全绿，含跨用户串数据的隔离断言。
