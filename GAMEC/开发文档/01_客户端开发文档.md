# 客户端开发文档

> 用途：前端（当前为**传统 HTML** 时间轴单页，后续封装客户端）的整体架构与实现约定。产品范围见 [[02_PRD_游戏日历|PRD v1.0]]，界面取值见 [[05_UI设计规范_游戏日历|UI 规范]]，数据获取见 [[03_Steam信息获取文档|Steam 信息获取]]。
> 原则：本文档只写「怎么搭」，不重复 PRD / UI 规范里已定死的需求与取值。
> **方向（v1.0）**：主视图 = 横向时间轴（范式 B），**先用传统 HTML 实现**；桌面客户端封装（Electron / Tauri）与液态玻璃悬浮形态延后到 V0.2，本文以「延后」标注。

## 1. 架构结论（传统 HTML 先行 + 后端多用户）

**有专用后端、面向多用户。** 用户以 **SteamID（Steam 登录）** 作为唯一标识，后端集中存储与采集数据。**前端当前 = 传统 HTML 时间轴单页**，跑通后再封装桌面客户端。

| 角色 | 实体 | 说明 |
|---|---|---|
| 前端（UI 层） | **传统 HTML 单页**（原生 HTML/CSS/JS），浏览器直接打开 | 时间轴主视图、日详情浮层、设置、首启、Steam 登录、提交 API Key |
| 后端服务 | 独立服务器（**Python FastAPI** + REST） | 用户管理（SteamID）、每日轮询采集、聚合、存储 |
| 数据库 | 多用户库（Postgres / SQLite） | users / games / play_days / achievements / screenshots |
| 通信 | **HTTP REST**（前端 ↔ 后端） | 接口见 [[05_后端接口文档|后端接口文档]] |

- **数据采集在后端**：后端用各用户提交的 API Key 每日轮询 Steam（`GetRecentlyPlayedGames` 记运行日 + `GetPlayerAchievements` 回填成就 + 社区截图接口记截图 / 运行日），前端无需常驻。
- **用户标识**：SteamID64 作为唯一 user_id，默认经 Layer 1 Steam OpenID 兑换（零客户端库）；Layer 2 侧车登录（node-steam-user）同样能兑换，v1.2 分层见 [[03_Steam信息获取文档|03]] §2a。
- **API Key 流程**：登录后引导用户到 `steamcommunity.com/dev/apikey` 申请，粘贴提交，后端加密存储。

## 2. 技术选型（v1.0：传统 HTML 先行，桌面壳延后）

| 层 | 当前（V0.1） | 后续（V0.2 起） | 依据 |
|---|---|---|---|
| 前端形态 | **传统 HTML 单页**（原生 HTML/CSS/JS） | Electron / Tauri 封装 | 先跑通时间轴，不引入桌面壳复杂度 |
| 时间轴渲染 | **手写 HTML/CSS/JS**（DOM + transform / scroll） | 同左，或换 React/Vue | 无框架依赖，浏览器直接打开 |
| Steam 登录 | **Layer 1 默认：后端纯 OpenID 重定向（零 SteamKit / node-steam-user 依赖）；Layer 2 opt-in：后端承担的 steam-session 侧车（node-steam-user，不变）** | 同左 | 前端只拿 opaque token（见 05），v1.2 见 03 §2a |
| 本地存储 | 后端 Postgres / SQLite；前端用导出 JSON | 同左 | 数据集中在后端 |
| 登录态 | 后端 opaque token | 同左 | 凭据不进前端 |

> **核心语言（Python 问题）**：核心**不用 Python**。核心进程是 Tauri 的 Rust / Electron 的 Node（取决于框架），而 SteamKit 是 .NET、node-steam-user 是 Node——Python 没有成熟的 Steam 客户端登录库。若后期想用 Python，仅作**离线脚本**（封面取色、数据迁移），不承担核心。若框架选 .NET（Avalonia / MAUI）可直接用 SteamKit 原库。

## 2A. 时间轴前端实现方案调研（2026-08-27）

> 调研范围：V0.1 `timeline/` 单页的**渲染与交互实现方案**。判定基线 = 范式 B + 传统 HTML 单页（§2、§8、[[02_前端功能文档]] §2、[[07_视图范式_游戏日历]] §4）。不合基线的方案不进入对比，仅在 A.5 记为延后。

### A.1 判定口径

1. 原生 HTML/CSS/JS，**无框架、无构建步骤**；
2. 浏览器直接打开即可运行（后续 V0.2 才进 Electron / Tauri 壳，届时渲染层为 Chromium / WebView2）；
3. 浅色、桌面浏览器视口；
4. 必须能承载：中心轴 + 上时点 / 下截图、边缘滚动（微延时）、**变化坐标（多尺度分段）**、日 / 周 / 月缩放；
5. 只服务当前基线，不为 A / C / D 范式提前铺渲染层（[[07_视图范式_游戏日历]] §9）。

### A.2 现成时间轴库评估（结论：均不作渲染层）

| 方案 | 渲染 | 依赖 | 授权 | 实用规模 | 判定 |
|---|---|---|---|---|---|
| **vis-timeline** 8.5.1（2026-05-07） | DOM | 无框架，standalone UMD 可 `<script>` 直引 | Apache-2.0 / MIT | ~2–3k items | 合基线但**不采用** |
| TimelineJS3 | DOM | 无框架 | MPL-2.0 | ~200 事件 | 不符 |
| Frappe Gantt | SVG | 无框架 | MIT | 甘特语义 | 不符 |
| react-calendar-timeline | DOM | **React 绑定** | MIT | ~2–3k | 不符（违反 1） |
| ApexCharts timeline | SVG | 通用 | MIT | ~2k | 不符（图表语义） |
| ScheduleJS / Highcharts Gantt | Canvas / SVG | Angular / 通用 | **商业授权** | 10k–100k+ | 不符 |
| D3 | SVG / Canvas | 通用 | ISC | 视实现 | **仅取计算子集**，见下 |

**vis-timeline 不采用的理由**（唯一一个通过基线过滤的候选，需说明）：它的信息范式是「左侧分组 + 横向轨道条（item / range / group）」，与范式 B 的「中心轴 + 轴上时点 / 轴下截图」不同构；其 Range 是**线性**时间→像素映射，而我们的**变化坐标要求非线性分段**，改这一层等于替换其内核；同时它自带整套交互（条目拖拽 / 编辑 / 分组）与 CSS，需大面积覆盖；standalone 包对一个「浏览器直开」的单页偏重。改造成本高于自研。

**D3 的取舍**：不引 `d3-selection`（引入即等于引入渲染框架），但 `d3-scale` + `d3-time`（+ `d3-time-format`）是**纯计算、无 DOM 依赖**，提供 `scaleUtc / ticks / tickFormat（多尺度格式）/ invert / nice`，可直接支撑刻度分级。**建议：先自写 `lib/scale.js`，但接口形状对齐 d3（`scale(t)→x`、`scale.invert(x)→t`、`scale.ticks()`）**，将来要换成 d3 不用改调用方。

### A.3 推荐方案：自研三层（数据 / 坐标 / 渲染）

对应 §4 的 `timeline/lib/`：

- **数据层** `mock-data.js`：**按定稿的 `/timeline` 出参形状先行**（v2.0 改：不再复用 `game-calendar` 的 `getDayGroups` / `getDayDetail`，那是月历口径），先纯 mock。
- **坐标层** `lib/scale.js`：**全页唯一坐标真源**。
  - `pxPerDay` 按缩放档（月 / 周 / 日）取值；
  - **变化坐标 = 分段线性 scale**：按数据密度把时间切段，每段一个 `pxPerDay`（密段展开、疏段压缩），`scale(t)` 分段累加、`invert(x)` 二分反查。比 fisheye / 对数可控，刻度好标、可缓存。分段阈值与「渐变 vs 跳变」是 PRD §8 未决项，交 spike 定。
  - **时间基准用 UTC**（Steam 时间戳是 unix 秒），本地时区只在格式化时套用；避免 DST 下「一天 ≠ 24h」造成坐标漂移（d3 文档亦建议优先 `scaleUtc`）。
- **渲染层** `timeline.js`：视窗虚拟化 + 节点池，位置一律 `transform`，不改 `left/top`。

### A.4 逐项技术选型

**1｜滚动机制 —— 自管虚拟滚动（`transform: translate3d(x,0,0)`），不用超长元素 + 原生滚动条。**
- 变化坐标下「滚动距离 ≠ 时间距离」，用原生滚动条要反算位置、缩放时还要重算 `scrollLeft`，成本高于自管；
- 元素尺寸上限：Chromium ≈ 16,777,216px、Safari ≈ 33,554,428px。按日视图 200px/天 计，Chromium 上限约 229 年（当前够用），但更高 `pxPerDay` 或将来更细尺度会触顶；自管方案无此上限；
- 代价：需自实现键盘导航（`←/→` `PageUp/Down` `Home/End`）、触控板惯性、滚动条 UI（`role="scrollbar"` + `aria-valuenow`）；
- 可选折中：保留一个仅用于产生原生滚动条与惯性的 `overflow-x: auto` 代理层，内容仍用 transform 摆放——**二者取其一，不得并存两套位置真源**。

**2｜输入**
- 平移拖拽：Pointer Events + `setPointerCapture`，容器 `touch-action: none`，移动量在 rAF 内合并；惯性 = 速度采样 + 指数衰减。
- 滚轮：`deltaX` / `Shift+deltaY` → 平移；`Ctrl+deltaY` → 缩放（触控板捏合在浏览器里即 `ctrlKey` wheel）。监听须 `{ passive: false }` 才能 `preventDefault()` 拦住页面缩放。
- **边缘滚动（微延时）**：指针进入左 / 右边缘带（建议 48–64px）后 `setTimeout` **120–200ms** 再启动 rAF 循环；速度 = f(距边缘距离)（线性或二次）；离开边缘带 / `pointerleave` 立停；`visibilitychange` 隐藏时暂停循环。

**3｜缩放（日 / 周 / 月）**
- 只改 `pxPerDay` 与刻度粒度，**不重建 DOM**；
- 以指针为锚：先 `invert(x_pointer)` 取 `t_anchor`，改档后用 `scale(t_anchor)` 反解 offset，保证锚点时间不动；
- 档位间 150–200ms 连续插值 `pxPerDay`（WAAPI 或自写 rAF easing），新旧刻度交叉淡入淡出避免跳变；`prefers-reduced-motion` 降为 120ms 淡入（[[02_前端功能文档]] §10）；
- 刻度多尺度格式参照 d3 `tickFormat` 的分级策略（年 / 月 / 周 / 日）。

**4｜虚拟化与性能**
- 只渲染 [视窗 − 1 屏, 视窗 + 1 屏]，节点池按事件 id 复用；
- 截图卡片等块用 `contain: layout paint`，可叠加 `content-visibility: auto` + **必须配 `contain-intrinsic-size`**（否则布局抖动）——该特性 Baseline 2024-09 newly available，可用；
- **DOM / Canvas 混合**：DOM 时间轴的实用规模在 2–3k items 量级，而成就 `unlocktime` 密度可能上万（§9 spike 3）。故**轴上密集时点 / 刻度用一层 `<canvas>` 绘制**（命中测试靠坐标反查，不建 DOM），卡片 / 截图 / 浮层仍是 DOM。既守住「传统 HTML、无框架」，又拿到绘制吞吐；
- 启用阈值建议：单屏可见时点 > 300 或全量事件 > 3k，实测再定。

**5｜截图带（轴下方，竖排每列 ≤ 5 张、超 5 增开一列）**
- `loading="lazy"` + `decoding="async"` + 固定 `aspect-ratio` 占位（防抖动）；IntersectionObserver 提前一屏预取；
- 只取后端缩略图，原图点击时再拉（P-12）；
- 图片解码是主线程尖峰：插入前 `img.decode()`，并发限制 4–6 张。

**6｜动效**
- **不采用 CSS scroll-driven animations**（`animation-timeline` / `scroll()` / `view()`）：MDN 标注 Limited availability，Firefox 未实现，非 Baseline；V0.1 要「浏览器直接打开」，不能假定 Chromium。改用 rAF + `transform` / `opacity`；
- 动画只碰 `transform` / `opacity`（合成层），不碰布局属性。

**7｜浮层（V0.1 = 时点悬浮 panel；底部 L3 日详情浮层已归档，不复用）**
- `popover` 属性 + `:popover-open`：Baseline newly available 2025-01，可用（用于时点悬浮 panel）；
- **CSS anchor positioning 只作渐进增强**：2026-01 才 newly available（Firefox 147），对「浏览器直开」的用户面偏新；主路径用 JS 定位（时点 panel 锚在标记正上方，用 JS 算位置）；
- `scrollend` 事件 Safari 26.2 才补齐，作增强用，兜底用 rAF / timeout 判停。

**8｜可直接用的基线特性**（均 Baseline widely available）：CSS 自定义属性（[[05_UI设计规范_游戏日历]] §3 token）、Grid / Flex、`:has()`、container queries、`aspect-ratio`、`overscroll-behavior: contain`（拦横向返回手势与回弹）、`scroll-snap`（如需缩放档对齐，可选）。

**9｜工程形态（落地细节）**
- **`<script type="module">` 在 `file://` 下被 CORS 拦死**——「双击 index.html 直开」与 ES Modules **二选一**：
  - **方案 A（建议）**：保留 ES Modules，用 `python -m http.server` / `npx serve` 起本地静态服务；后端本就是 HTTP，前端走 `http://localhost` 链路一致，README 写一行启动命令即可；
  - 方案 B：全部经典 `<script>`（IIFE + 全局命名空间），可双击直开，模块化靠约定 —— 记为「离线单文件分发」备选。
- 字体本地打包 woff2 + `font-display: swap`，**Noto Sans SC 必须子集化**（全量 > 8MB）——对应 README 待办 5；
- 无构建 → 无 TS：用 JSDoc 类型注释 + 纯函数（`lib/` 已如此规划），保留将来上构建的余地。

### A.5 不采纳 / 延后（同步进 [[04_未来规划_游戏日历]]）

React / Vue / Svelte 及任何构建链；现成时间轴库作渲染层（vis-timeline 等）；CSS scroll-driven animations；全量 canvas / WebGL 渲染；CSS anchor positioning 作主路径。

### A.6 spike 补充（细化 §9 第 6 条）

- **6a** mock 生成 1k / 5k / 20k 事件，实测 DOM 方案与 DOM+canvas 混合方案在平移 / 缩放下的帧率与内存 → 定 canvas 启用阈值；
- **6b** 分段线性 scale 的分段阈值与视觉连续性（渐变 vs 跳变，PRD §8 未决）；
- **6c** 20–60 张缩略图同屏时的解码耗时与掉帧；
- **6d** 边缘滚动手感取值（延时 120 / 160 / 200ms × 速度曲线）。

## 3. 进程结构

- V0.1 前端是**传统 HTML 单页**：无宿主进程、无托盘、无悬浮窗，浏览器打开即用；数据通过 HTTP REST 走后端。
- 桌面封装（Electron / Tauri 宿主进程 + 系统托盘 + 无边框悬浮窗）延后到 V0.2（见 PRD §6）。

## 4. 项目结构（示意，V0.1 = 传统 HTML）

```
timeline/             # 传统 HTML 单页（范式 B 时间轴）
  index.html          # 入口（浏览器直接打开）
  styles.css          # 样式：颜色 / 事件色 / 组件沿用 05 通用 token
  timeline.js         # 时间轴渲染 + 边缘滚动 + 坐标精简
  day-detail.js       # 日详情浮层（点击时点标记）
  mock-data.js        # 本地 mock / 导出 JSON 喂入，跑通后换后端 REST
  lib/                # 时间轴布局、事件点 / 截图布局（纯函数）
```

## 5. 本地核心层职责

- **Steam 会话**：登录、登录态持久化、2FA、会话续期（见 03 文档）。
- **同步编排**：首次同步与增量同步的统一入口，产出到 SQLite。
- **主题色计算**：同步期算一次入库（`theme_color` / `source` / `at`），渲染期只读；规范化 + 对比度验算做成纯函数并加单测（UI 规范 §3.4、§9）。
- **本地存储**：SQLite 读写与迁移，见 §7。

## 6. 客户端通信

> 数据读写走**后端 HTTP REST**（见 [[05_后端接口文档|后端接口文档]]），本地仅剩 Steam 登录握手（SteamKit）。下列命令已并入后端接口，本地实现以 05 为准。

| 命令                 | 入参          | 出参                                                          | 说明                                                                                  |
| ------------------ | ----------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `steam_login`      | —           | 登录态 / 需要 2FA 的提示                                            | 触发登录流程                                                                              |
| `steam_logout`     | —           | —                                                           | 清除登录态                                                                               |
| `sync_now`         | —           | 进度事件流                                                       | 手动 / 托盘触发的全量同步                                                                      |
| `get_month_events` | year, month | `TimelineEvent[]`（聚合后）                                      | 日历格渲染所需的最小字段（事件类型、前 N 个 appid、数量）                                                   |
| `get_day_detail`   | date        | `{counts: {achievement, first_play, release}, rows: [...]}` | 日详情浮层                                                                               |
| `get_sync_status`  | —           | 状态 + 上次同步时间戳                                                | 底栏左                                                                                 |
| `export_json`      | 目标路径        | 结果                                                          | 一键备份                                                                                |
| `theme_color`      | —           | —                                                           | **无此命令**：主题色随同步入库，渲染期直接读 `get_month_events` / `get_day_detail` 返回的 `theme_color` 字段 |

> 事件数据在核心层聚合后再出（L0 只需「类型集合 + 数量 + 前几个 appid」），不要在渲染期全量拉取（调研 §2.5.8 的结论仍适用）。
> **时间轴数据（v1.0）**：V0.1 前端先纯 mock；接真数据时后端**一次性返回全量** `TimelineEvent[]` + `screenshots[]`，前端本地按范围 / 层级（日 / 周 / 月）过滤——不按范围多次请求，也不在渲染期逐月拉取。

## 7. 本地存储（SQLite 表）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `game` | appid、名称中/英、封面、开发商、发售日、`status`（wishlist/owned/played/released_wishlist）、`theme_color`、`theme_color_source`、`theme_color_at`、`cover_cache_path` | 含已发售归档的愿望单游戏（F-2） |
| `play_day` | game_id、date | 每日轮询，核心指标（运行天数） |
| `achievement_unlock` | game_id、achievement_id、`unlocktime` | 历史回填（过去运行状态） |
| `screenshot` | game_id、shot_id、`taken_at`（截取时间）、thumbnail_url、url、privacy | v0.7 新增，按日聚簇派生 `play_day`，缩略图进日详情 |
| `sync_meta` | last_sync_at、各源游标 | 增量同步 |

- `TimelineEvent` 由 `play_day` / `achievement_unlock`（按日聚簇）/ `game.release_date` 派生，可物化或查询期聚合。

> **存储形态（无后端）**：个人数据量很小——几百款游戏、万余成就、数千运行日、截图记录，结构数据约 **2MB**（封面图另存本地文件，JSON 里只存路径），**可不建数据库，用单个 JSON 文件**即可，启动时全量读入内存无压力。
> **跨设备同步**：无自有后端也能同步——把数据文件放进云盘（iCloud / Dropbox / Syncthing），App 只读写这一个文件，云盘负责同步，即可实现 Win ↔ 手机同步。SQLite 仅在需要复杂查询 / 聚合时选用；无论哪种，都保证一键导出为单文件。
- 无 `PurchaseIntent` 表（F-3 已移入 [[04_未来规划_游戏日历|未来规划]]）。

## 8. 构建与运行

- V0.1：**传统 HTML 单页**，无构建步骤，浏览器直接打开 `timeline/index.html`；数据先用 `mock-data.js` / 导出 JSON。
- 桌面封装（Electron / Tauri 无边框悬浮窗 + 托盘 + 拖拽）延后到 V0.2。
- 字体本地打包、不依赖在线字体（离线可用，PRD 本地优先原则）。
- 基准先在桌面浏览器视口下验证；缩放 / 拖动等桌面壳能力随封装再议。

## 9. 验证 spike 清单（先于界面开发）
