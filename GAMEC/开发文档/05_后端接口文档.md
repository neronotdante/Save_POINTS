# 后端接口文档

> 用途：多用户后端的设计与接口契约。上游 [[02_PRD_游戏日历|PRD]]（多用户 + 后端）、[[01_客户端开发文档|客户端开发文档]]、[[03_Steam信息获取文档|Steam 信息获取]]。
> 定位：**面向多用户**；用户以 SteamID 唯一标识；后端集中存储并每日采集 Steam 数据。

## 1. 架构

- 客户端（桌面悬浮 + 未来手机）↔ 后端 REST API ↔ 数据库。
- 后端技术栈：**Python FastAPI**；数据库：**Postgres**（多用户，至少 2+ 并发）。
- 后端负责：用户管理（SteamID）、每日轮询采集（用各用户 API Key）、聚合、存储。
- **数据采集在后端跑定时任务**，客户端无需常驻（解决"自动运行暂存脚本"）。
- **愿望单默认由后端自己拉**（`IWishlistService/GetWishlist`，免 Key，公开愿望单直接查，见 03 §2a）；`POST /wishlist` 客户端推送仅作兜底（对方愿望单私密、后端拿不到时使用），不再是主路径。

## 2. 用户与认证

- **唯一标识 = SteamID64**（Steam 登录获得）。
- 流程（Layer 1，默认）：Steam OpenID 2.0 重定向 → 后端验签取 SteamID → 创建或绑定用户 → 引导到 `steamcommunity.com/dev/apikey` 申请 → 粘贴提交 → 后端加密存储。**不再要求客户端先跑 SteamKit 换 access_token**（该路径降级为 §7 决策里保留给未来原生客户端的备用分支，见 07 §2.3）。
- **愿望单**：后端用 SteamID64 直接调 `IWishlistService/GetWishlist`（免 Key），私密愿望单查不到时才需要 Layer 2 的 web session cookie；`POST /wishlist` 客户端推送保留作兜底。
- **登录态**：登录后发一个**简单 opaque token**（随机串存库，映射 steamid），客户端每次请求带 `Authorization: Bearer <token>`；**不实现 JWT / session cookie**。
- **登录分层（v1.2，2026-08-28 定案）**：默认走 **Steam OpenID 2.0**（`GET /auth/steam/openid/login` + `/callback`，零密码、零侧车依赖，只换 SteamID64）；愿望单 / 购买历史 / 私密截图才需要用户 opt-in 升级到现有 steam-session 侧车登录（Layer 2）。分层依据、各数据源在 Layer 1 下能否公开拿到，见 [[03_Steam信息获取文档|03]] §2a。

| GET | `/auth/steam/poll` | — | `{ status, user_id, token }` | 轮询登录结果，成功后加密存会话 |

| DELETE | `/auth/apikey` | — | `204` | 解绑 Key（§6「解绑 / 吊销」出口）；已采集数据保留，只停同步（v1.4） |
| GET | `/auth/apikey` | — | `{ has_key }` | 是否已绑 Key |
| GET | `/calendar/{year}/{month}` | — | `TimelineEvent[]` | 日历事件（后端聚合后） |
| — | **`TimelineEvent.minutes`**（v1.5 新增） | — | `int \| null`，当日第几分钟（0~1439） | 成就簇取该 (游戏, 日) **最早**一次解锁；购买取真实下单时刻；发售 / 首玩无精确时间戳，按惯例值 01:00 / 12:00。与 `DayRow.time` 同一口径同一来源。**没有它就没法说「当天第一件事是什么」**：出参里只有 `date`（到日），同一天的事件按 `(date, type)` 排序落到客户端手里，`type` 是字符串序，同类型之间更是数据库扫描顺序——客户端据此挑出来的「第一个成就」是个任意值。前端用它挑时点的代表游戏（[[07_视图范式_游戏日历\|07]] §4.2k） |
| GET | `/calendar/day/{date}` | — | `{ counts, rows, screenshots[] }` | 日详情浮层（含当日截图缩略图） |
| GET | `/calendar/timeline` | `If-None-Match`（可选） | `{ events: TimelineEvent[], screenshots: Screenshot[], games: Game[] }` + `ETag`；命中则 `304` | 时间轴（范式 B）一次性全量数据（[[07_视图范式_游戏日历\|07]] §4.7）；`games` 带生命状态，供封盘帽与「隐藏从未启动」在前端本地过滤。**带弱 ETag**（v1.3 新增）：全量出参在大库上不小、两次同步之间又完全不变，客户端回带 `If-None-Match` 时先比指纹，命中直接 304——指纹只跑几条计数查询，**连聚合都不做**；指纹含 `user_id`，不会跨用户命中。**必须同时给 `Cache-Control: no-cache`**（v1.4）：只给 ETag 而不给新鲜度信息时，浏览器会按 RFC 9111 的启发式缓存自行给响应估一个保质期，在这段时间里直接吃本地副本、连一次条件请求都不发——症状是同步完刷新页面拿到的还是旧数据且毫无报错。另需在 CORS 上 `expose_headers=["ETag"]`，否则跨源下前端 `res.headers.get('ETag')` 恒为 `null`，`If-None-Match` 根本发不出去。**⚠️ 指纹里必须带出参形状版本 `_SHAPE_VERSION`，改出参形状（加字段 / 改字段含义）就要 +1**：指纹只按数据算的话，后端加了字段指纹不变，客户端一直吃 304、拿着旧结构的缓存体，新字段在前端永远是 `undefined`，而且没有任何报错（`theme_color_source` 那次踩过，`minutes` 这次同理） |
| GET | `/achievements/{appid}/{date}` | — | `AchievementDetail[]`（成就名 / 图标 / 全球解锁率 / 解锁时间戳） | **v2.0 新增**：时点悬浮 panel 的成就形态按需懒加载；明细不进 `/timeline` 全量出参（体积）。日期按 UTC 计日，与时间轴一致；游戏不属于该用户 / 当日无解锁均返回空数组（不是 404——悬浮取数不该以错误呈现） |
| POST | `/wishlist` | `{ items: [{appid, priority}] }` | — | 客户端拉取愿望单后提交 |
| POST | `/sync` | — | 进度事件流 | 手动触发同步 |
| GET | `/games` | — | `Game[]` | 游戏库；每条含 `lifecycle`、`shelved_at`、`launched_ever`、`play_days_count`、`ach_unlocked`、`ach_total`（[[02_PRD_游戏日历\|PRD]] §3 生命状态）。与 `/calendar/timeline` 的 `games[]` **同一份构建逻辑**，口径不会漂。`playtime_forever` 不出参——只供后端判定，界面上「玩得久不久」只有 `play_days_count` 一个口径 |
| POST | `/games/{appid}/review` | `{ rating, comment }` | — | 短评评分（P-5） |

### 3.1 OpenID 回调的前端回跳（v1.3，2026-09-03）

浏览器前端登录必须能**自动回到应用**。回调原先直接返回 JSON，用户授权完只看到一坨 JSON、没有任何返回路径——这是「点了登录就回不来」的直接原因。

- 配置 `GC_FRONTEND_BASE_URL`（默认 `http://localhost:5173`）后，验签成功 302 到 `{前端}/#token=…&user_id=…`，失败 302 到 `{前端}/#error=…`。
- **v1.4 回跳来源**：前端发起登录时带 `?front=<location.origin>`，后端只接受 `GC_CORS_ORIGINS` 里的源（否则是开放重定向），记进 10 分钟的 `gc_front` cookie，回调优先按它跳、没有才回落到 `GC_FRONTEND_BASE_URL`。这样后端托管（8000）与 serve.py（5173）两种起法都无需改配置。
- **v1.4 前端托管**：`GC_SERVE_FRONTEND=true`（默认）时后端把 `timeline/` 挂在 `/`，前后端同源；根路径不再重定向到登录。
- **token 走 URL fragment 而不是 query**：fragment 不会被浏览器发往服务端，不进访问日志与 `Referer`；前端取到后立即 `history.replaceState` 清掉。
- 该地址**必须同时在 `GC_CORS_ORIGINS` 里**，否则跳回去也调不通接口。
- 留空时沿用旧的 JSON 行为，供 curl / 非浏览器客户端调试。

> ⚠️ **前端端口不得用 8080**：Steam 客户端的 CEF 远程调试固定占用 8080（`steamwebhelper.exe --remote-debugging-port=8080`）。本产品的用户必然开着 Steam，撞端口是必然——那时浏览器打开 8080 得到的是 Steam 调试页而非本应用。默认改用 5173，CORS 默认值同步调整。

### 3.2 `/sync` 的进度粒度与并发保护（v1.3，2026-09-03）

首次同步要逐款打 Store API 补元数据 + 下封面（各 1~2s，串行），**297 款的库实测约 22 分钟**。这一步曾经是「点了同步就没有任何响应」的直接来源，四个问题合起来造成：

| 问题 | 后果 | 现在 |
|---|---|---|
| `owned_games` 阶段只在**全部跑完后**发一个事件 | 几十分钟里前端一个事件都收不到 | 每 `OWNED_BATCH`(=10) 款产出一次 `{status:"running",processed,total}`；**开跑即先报 total**，前端立刻显示 `0 / 297` |
| 整个阶段跑完才提交事务 | 中途关页面 / 重启，**一条都不落库** | 每批 `commit()`，中断后已拉到的部分保留，下轮继续 |
| 同步锁是无超时的 `set` | 客户端断开后生成器卡在 `yield`，锁**永不释放**，此后每次同步都 409「同步正在进行中」，只能重启后端 | 锁带心跳时间戳，超 `SYNC_STALE_SECONDS`(=600s) 无心跳可被抢占；每产出一个事件续期 |
| SQLite 无 WAL / 无 `busy_timeout` | 同步长时间持写事务，期间前端拉数据、甚至认证写 `last_used_at` 都 `database is locked` → 500 | 连接期设 `journal_mode=WAL` + `busy_timeout=15000`，读写并发 |

> **`pillow` 是必需依赖，不是可选**：`services/theme.py` 的本地取色靠它。它缺失时 `pick_color_from_cover` 在第一行 `from PIL import Image` 就 ImportError 返回 None，**全库主题色回退成同一个 `#6D4AE0`**（PRD P-11「成就标记用游戏主题色」直接失效），而封面**照样每款下载一遍再丢掉**——297 款白花约 10 分钟。已加入主依赖；同时 `_apply_theme_color` 在取色能力不可用时**跳过下载**，并且只把 `source ∈ {local, api}` 当作「已完成」——`fallback` 是「这次没取成」，装上依赖后会自愈重取。

### 3.3 三类数据「拉不到」的三种不同原因（v1.4，2026-09-05）

同步跑完、无报错，但截图 / 购买 / 愿望单全是空——三者原因完全不同，别当成同一个问题查：

| 数据 | 状态 | 原因 |
|---|---|---|
| **截图** | ✅ 已修复 | `?xml=1` 这个老参数**已失效**——带上它 Steam 返回的仍是整页 HTML。`parse_screenshots_xml` 拿 HTML 去 `ET.fromstring` 必然 ParseError → 返回空 → 被上层当成「该用户没有公开截图」静默跳过，日志里看不出问题。已改为解析 HTML（`parse_screenshots_html`，XML 分支保留作回落）。实测该用户 50 张/页、150 张入库。 |
| **愿望单** | ✅ 已修复 | 官方 `IWishlistService/GetWishlist` **免 Key 免登录**就能读公开愿望单（§7 定案），但调用被包在 `if session:` 里——只走 Layer 1 OpenID 的用户永远拿不到。已移出该分支，cookie 变成可选参数。实测 48 条。 |
| **购买记录** | ⚠️ 设计限制，非缺陷 | 购买历史**没有公开路径**，只能用 web session cookie 拉（Layer 2 opt-in，见 03§2a）。仅 OpenID 登录的用户拿不到。现在无会话时明确产出 `{"step":"purchase_history","status":"skipped","reason":...}`，让前端能解释「为什么没有购买记录」，而不是让这一类数据静默缺席。 |

> **截图的时间精度**：社区页面只在**日期分组标题**上给日期（可能是跨日范围），单张截图没有精确时刻，取分组起始日 0 点。PRD §3 里截图的用途是「按日聚簇派生 PlayDay」、时间轴也只按日挂载（07§4.5），日粒度够用；要精确到秒得逐张打 filedetails 页，一张一个请求，不值得。

> **`upsert_play_day` 必须 `flush()`**：会话是 `autoflush=False`，`db.add()` 后对象还在 pending，紧接着的 `select` 查不到。同一游戏同一天多张截图时（截图按日聚簇派生运行日），同一个 `(user, game, date)` 会被连着 upsert 多次、每次都判「不存在」，提交时 UNIQUE 约束炸。这个 bug 被截图解析失效掩盖了很久——截图一直是 0 条，「同一天多张」的场景从未发生过。

> 至少 2+ 并发用户，选 **Postgres**；单用户自托管可用 SQLite。

| `users` | steamid(主键)、nickname、avatar、apikey_enc、created_at |

## 5. 每日采集任务

- 定时任务 per user：用其 API Key 轮询 `GetRecentlyPlayedGames`（记 `play_days`）；回填 `GetPlayerAchievements`（记 `achievements`）；拉取社区截图元数据（记 `screenshots`，按日聚簇派生 `play_days`）；用存储的 web session cookie 拉取购买历史（记 `purchases`，日粒度）与愿望单 / 私密截图。
- **`GetOwnedGames` 每轮都拉**（v1.3 修正原「仅首次回填」）：`playtime_forever` / `rtime_last_played` 是封盘判定的输入，必须跟着最新一次启动走；**元数据补全（Store API 逐 appid）只在首次同步做**——量大且慢，之后靠 `enrich_game_metadata` 按需刷新。
- **成就回填是增量 + 分批的**（v1.3 新增）：
  - **增量判据 = `games.achievements_at`**：`NULL`（从未回填，先补「过去」）或 `< last_active_at`（回填后又玩过，需重拉捕获新解锁）才入队；两者都不满足的本轮跳过。**无成就的游戏同样盖 `achievements_at`**，不会像按「achievements 表有无记录」判断的旧写法那样每轮重试一遍。
  - **分批**：单轮上限 `GC_ACHIEVEMENT_BATCH_SIZE`（默认 50）——每个游戏要打 2~3 次上游接口，首次同步的大库不能在一轮里全跑完；剩余的下一轮继续，靠 `achievements_at` 自然推进，不需要额外游标。
- **每次采集收尾重算生命状态**（v1.2 新增）：拉一次 `GetOwnedGames` 取 `playtime_forever` + `rtime_last_played` → 与本地三路来源取 `max` 作 `last_active_at`（= 最后一次启动时间）→ 按 [[02_PRD_游戏日历|PRD]] §3 的阈值算 `lifecycle` / `shelved_at`，写回 `games`。**只在采集后算，不在请求期算**——`/timeline` 要一次性返回全量，判定必须是读库即得。
- 阈值是**服务端常量**（`T_quiet=45d`、`T_time=600min`、`T_ach=10%`，落在 `app/services/lifecycle.py`），改动后用 **`game-calendar-recompute`** 命令行入口一次性重算全库（可带 SteamID 只重算指定用户）；重算**幂等且无状态**——只看当下的 `last_active_at`，不读上一次的 `lifecycle`，所以再次启动会自然回落到 `active` 并清空 `shelved_at`，无需回滚逻辑。`lifecycle_at` 记最近一次算的时间。
- 判定的一个边界（文档原先未定）：**启动过但拿不到任何时间证据**（`playtime_forever > 0` 却无 `rtime_last_played`、无运行日 / 成就 / 截图）时无法算沉寂天数，保守归 `dormant`——轴上不画标记，不会误报封盘。
- 失败重试 + 指数退避；单用户失败不影响他人；采集结果落库，客户端只读。
- **首轮同步的成本控制**（v1.3 新增）：首轮要为全库游戏补元数据，是整条链路最慢的一段。已落三条：
  ① `SteamClient` 复用单个 `httpx.Client`（原先每请求新建，每次重做 TCP+TLS 握手，实测单请求 1890ms → 222ms）；
  ② 英文名不重复拉——`GetOwnedGames` 已给英文名，仅当本地 `name_en` 为空才为英文再打一次 Store API；
  ③ 截图只对 `launched_ever` 的游戏拉（**不能用 `play_days` 当判据**：首轮它只有近两周数据，会漏掉历史截图）。
  仍未做的结构性改动：**把元数据补全整体移出首轮**，首轮只建骨架（`GetOwnedGames` + 成就 + 运行日 + 重算 lifecycle）让时间轴先可用，元数据交后台按 `metadata_at` 增量分批补——封面缺失本就有降级渲染（[[05_UI设计规范_游戏日历|05]] §5 占位规则、[[07_视图范式_游戏日历|07]] §4.8），首轮无封面是设计内状态。见 §8.5。

## 6. 安全与合规

- API Key **加密存储**（服务端密钥 / KMS），日志不落 Key，接口不回显 Key。
- **Steam 会话（web cookie + refresh token）**：经用户授权可上传 `sessionid` / `steamLoginSecure` / `refresh_token`，Fernet 加密存储（与 API Key 同待遇），仅用于拉取该用户自己的愿望单 / 私密截图 / 购买历史；提供「解绑 / 吊销」出口；**不存账号密码、不存客户端协议登录凭据。** Layer 1（OpenID）连这条例外都用不上——全程不产生、不接触任何账号密码或会话 cookie，只做一次签名校验。
- 后端只存用户自己的 Steam 数据，用户间隔离（按 steamid 过滤）。
- 登录态：最简 **opaque token**（不实现 JWT / session cookie）；接口**最低程度限流**（防滥用即可）。
- 隐私政策：Steam Key 不得分享给第三方的 ToS 边界——自托管 / 用户自有 Key 场景可接受，公开多用户需谨慎。

## 7. 已决策

- 后端技术栈 = **Python FastAPI**。
- 数据库 = **Postgres**（多用户，至少 2+ 并发）。
- 愿望单 / 私密截图 = **后端用存储的 Steam web session cookie 拉取**（用户授权上传、加密存储；客户端推送 `/wishlist` 为兜底）。
- 账号密码 / SteamKit 登录凭据仍留在客户端、不上传；**许可证入库时间（TCP 协议 `CMsgClientLicenseList`）已放弃**，不采集、不落库。
- 购买时间 = **商店购买历史页**（web cookie，后端自主，日粒度；见 [[03_Steam信息获取文档\|03]] §4.1）。
- Steam 登录 = **steam-session 侧车 + 500×500 登录页**（扫码 QR 为主、账号密码为辅；侧车导出 `sessionid`/`steamLoginSecure`/`refresh_token`，后端加密存储，密码不落盘）。
- 部署形态 = **本机（开发）→ 云（发布）**。
- 接口限流 = **最低程度**（防滥用即可）。
- 登录态 = **最简 opaque token**（不实现 JWT / session cookie）。
- 游戏库来源 = **`GetOwnedGames`**（§8.2 缺口 F 的决策）。**v1.3 修正**：原定「一次性回填、非每日差分」，但 `playtime_forever` / `rtime_last_played` 是封盘判定（PRD §3）的输入，必须跟着最新一次启动走，故改为**每轮都拉**；「一次性」的部分收窄为**元数据补全**（逐 appid 打 Store API，量大且慢，只在首次同步做）。
- 登录分层（v1.2）= **Layer 1 Steam OpenID 默认 + Layer 2 现有侧车 opt-in**；愿望单改走官方 `IWishlistService/GetWishlist`（公开愿望单免 Key/免登录），截图沿用现有「公开免登录、私密走 cookie」；购买历史无公开路径，仍强制 Layer 2。详见 [[03_Steam信息获取文档|03]] §2a。

### 8.3 小项（2026-08-27 原始记录，多数已消解；仍成立的已并入 §8.5）

- **`name_zh` 全库恒为 NULL**：Store API 用 `l=schinese` 取回的中文名被写进了 `name_en`；§4 要求「名称中 / 英」，字段语义现在是错的。
- **愿望单 `priority` 只接收不落库**（`Game` 无该字段，V0.1 无消费方）。
- **元数据永不刷新**：`get_or_create_game` 只在字段为 `None` 时写入，改期 / 改名 / 换封面都不会更新。
- **CORS 默认过宽**：`allow_origins=["*"]` + `allow_credentials=True`，实测任意 Origin 都拿到 `ACAO` 回显 + `ACAC: true`（Bearer 不由浏览器自动携带，危害有限，但生产必须收紧）。
- **登录态无出口**：无登出 / 撤销接口，`auth_tokens.last_used_at` 从不更新，过期 token 无清理。
- **任务级重试形同虚设**：`retry_with_backoff` 对 `SteamError` 直接 re-raise，§5 的「失败重试 + 指数退避」实际只有 `SteamClient` 内部那一层。
- **登录链路从未验证**：`ISteamUserOAuth/GetTokenDetails` 是老接口，仍是 [[01_客户端开发文档|01]] §9 里最高风险、尚未做的 spike。已有定案缓解方案见本文档 §7「登录分层」与 [[03_Steam信息获取文档|03]] §2a（Layer 1 OpenID），但尚未实现。
- **愿望单接口已过时**：`services/steam.py::get_wishlist` 调的 `wishlist/profiles/{steamid}/wishlistdata/` 已被 Steam 废弃（约 2024-11），应改打官方 `IWishlistService/GetWishlist`（免 Key，公开愿望单直接查，私密才降级 session cookie），见 [[03_Steam信息获取文档|03]] §2a。

### 8.5 剩余项（2026-09-02 之后）

按处理顺序：

1. **登录链路的真机验证**（最高风险，仍未做的 spike）：Layer 1 OpenID 已实现但未在真实回调下跑通；`ISteamUserOAuth/GetTokenDetails`（`POST /auth/steam`）是老接口，可用性未验证。见 [[01_客户端开发文档|01]] §9。
2. **上游客户端与 SSE 的测试覆盖**：`services/steam.py` 的网络路径、`/sync` 的 SSE 事件流、scheduler、限流仍未覆盖（纯函数解析器已有测试）。
3. **`GetOwnedGames` 的元数据刷新节奏**：目前只在首次同步逐 appid 打 Store API，之后改期 / 改名 / 换封面要靠愿望单提交或购买历史顺带触发，没有独立的定期刷新任务。
4. **`purchases` 的 subid 展开**：DLC / 捆绑包需 PICS 映射，当前跳过（03 §4.1 回退链第 2 档）。
5. **Postgres 上的实测**：迁移与测试目前都在 SQLite 上跑通，Postgres 只在 `docker-compose` 里装配过，未在真库上验证过 `0002_lifecycle`（`batch_alter_table` 在 Postgres 下退化为普通 `ALTER`，风险低但没实测）。
6. **首轮同步仍偏慢（结构性）**：§5 的三条提速做完后，瓶颈从「握手浪费」转移到「Store API 限流」（经验值约 200 req/5min，非官方文档，需实测校准）。解法是把元数据补全移出首轮、改后台渐进补全：给 `games` 加 `metadata_at`，复用成就那套「增量 + 分批」队列。首屏时间可从几十分钟降到 1~2 分钟。
7. **封盘阈值的真库标定**：`T_quiet=45d` 等三个值尚未在真实数据上跑过，PRD §3 已注明「真库跑过后回 §3 调」。
